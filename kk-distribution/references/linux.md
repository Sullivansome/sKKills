# Linux distribution

There is no single native signature scheme covering every Linux artifact. Choose the formats and client trust path explicitly. This collection requires publisher signatures for every distributed payload, plus the native package/repository trust appropriate to its channel.

## Debian/Ubuntu: DEB and APT

Build a correct `.deb` with metadata, dependencies, architecture and safe maintainer scripts. Sign repository release metadata (`InRelease`, or `Release` plus `Release.gpg`) after generating package indexes with hashes of the final package bytes. Distribute the repository verification key through a trusted path and restrict it to that source with `Signed-By`. Do not use `trusted=yes`, insecure-repository options, or signature bypasses.

APT normally authenticates repository metadata and the resulting package-hash chain; it does not thereby validate an embedded per-package publisher signature. Provide a detached signature on each `.deb` for the signed-only direct-artifact requirement, and a verifier for direct downloads before `dpkg` executes maintainer scripts. Repository installs rely on the configured archive trust chain. Do not claim plain `dpkg -i` verifies your detached signature. See [apt-secure](https://manpages.debian.org/stable/apt/apt-secure.8.en.html).

Publish package files first, then consistent signed indexes/metadata atomically. Test fresh install, upgrade and removal from a clean supported Debian/Ubuntu system, including rejection of untrusted metadata and changed packages. Retain old packages needed by supported clients or recovery plans.

## Fedora/RHEL family: RPM and DNF

Sign the final RPM with the approved OpenPGP signing identity using the installed RPM version's supported `rpmsign --addsign` path; verify with the matching RPM tooling and trusted expected key. Generate repository metadata after package signing, then sign the repository metadata as supported by the repository manager. Configure and test both package signature checks and repository metadata checks (commonly `gpgcheck=1` and `repo_gpgcheck=1`); check local-package policy separately for direct installs.

Test a clean client with the intended key provisioning, supported crypto policy, upgrade behavior, and signature failure cases. Do not use `--nogpgcheck`. The [RPM signing manual](https://rpm.org/docs/6.1.x/man/rpmsign.1) describes signing mechanics; select documentation matching the installed RPM/DNF versions.

## Archives and AppImage

Sign each final tarball/AppImage with an approved detached-signature scheme, and sign the version/platform/digest manifest. An AppImage's optional embedded signature is not evidence that a user's launch path verifies it. Verify the detached signature and trusted signer before extraction or execution; test rejection of altered files and an unexpected key.

The bootstrap CLI installer demonstrates OpenSSL SHA-256 detached verification with an embedded trusted RSA public key, plus a signed version-bound checksum manifest. Its public key must be provisioned through a trusted bootstrap; release keys are not generated by the template. It does not implement native package installation or OS notarization. If using another scheme such as OpenPGP, Minisign or Sigstore, implement that verifier explicitly and pin the expected fingerprint or identity/issuer policy; accepting any cryptographically valid signer is insufficient.

Authenticate an installer script before running it; do not pipe an unverified download to `sh`. Confirm executable architecture, libc/system requirements, installation permissions and safe replacement. Hashes and signatures must describe bytes after every packaging/signing operation. Never publish a mutable latest URL as the sole identity of the artifact being verified.

Signing keys need rotation and revocation procedures. A trusted key does not automatically provide freshness or rollback protection: bind the release version and enforce an explicit update policy, especially for unattended updaters.
